# 校园失物招领系统 —— 细化需求说明（简化版）

> 本文件是当前唯一有效的需求契约。技术栈：Next.js 16.3.6 + React 19 + Tailwind v4 + shadcn v4（Base UI）+ Supabase（本地 podman）。
> 本轮做了大幅简化：**取消答题验证、人工审核、标签体系、寻物启事、草稿系统与相似度匹配**。

---

## 1. 范围

**做**：账号系统、发布招领（拍照 → AI 生成名称与描述 → 电话或位置）、失物墙（公开浏览）、实名领取、我的页面。

**不做**：答题验证、人工审核、寻物启事与匹配、标签体系、草稿、通知推送、地图 SDK、云端部署。

---

## 2. 账号

- 用户名 + 密码；用户名映射为内部邮箱 `<username>@<NEXT_PUBLIC_AUTH_EMAIL_DOMAIN>`（默认 `campus.local`）。
- 不做邮箱验证。用户名 `^[a-z0-9_]{3,20}`$D`，统一小写、唯一。
- 除 `/login`、`/signup` 与静态资源外，所有页面与 Server Action 都要求已登录。

---

## 3. 核心流程

### 3.1 发布招领（三步向导，一步一屏，无草稿）

界面按「一步一屏」拆成三个独立屏幕（细节与文案见 `docs/UI-DESIGN.md`）：

**第 1 屏 · 拍照**

1. 拍照 1–5 张（移动端 `capture=environment`），浏览器端压缩（最长边 ≤1600px、质量 0.8、≤2MB）后逐张上传。这一屏只做拍照，不放任何其它表单项。

**第 2 屏 · 确认信息** 2. 进入即自动调用视觉模型读取全部照片，生成**物品名称**与**物品描述**（用户不需要先点「识别物品」）。3. 名称与描述**可编辑**；识别失败不阻塞，用户可手填，也可点「识别物品」重试；照片集合变化后重新识别。

**第 3 屏 · 怎么还** 4. 选择保管方式：

- **代为保管** → 必填联系方式（5–100 字，通常是手机号）
- **留在原地** → 优先取浏览器定位坐标；拒绝定位权限时必须填写位置描述

5. 点「发布」→ 一次事务写入物品与全部照片记录 → 成功后整屏对勾正反馈 → 回到失物墙。
6. AI 调用失败时，用户可**手填名称与描述**继续发布（不阻塞）。

### 3.2 失物墙（公开浏览）

- 首页即失物墙：**双列瀑布流**，卡片展示**图片、名称、描述（截断）、发布时间**。
- **已认领的物品仍然留在墙上**，卡片上带「已认领」标签（未认领的不加标签，保持简洁）。
- 分页「加载更多」，每页 `app_config.page_size`（默认 20）条，到底显示「没有更多了」。
- **卡片与详情页永远不出现联系方式与位置** —— 它们在数据库层就对客户端 REVOKE。
- 详情页展示全部照片（**支持左右滑动切换**）、完整描述；未认领时提供「我要认领」入口（跳转到独立的认领屏）。

### 3.3 实名认领（认领即归属）

1. 在详情页点「我要认领」→ 进入**独立的认领屏**（不是详情页里的一张卡片），填写**真实姓名（2–20 字）**与**手机号**。
2. 提交成功后：物品**立即被标记为「已认领」**，并**立即揭晓**拾主的联系方式（代为保管）或位置（留在原地）。
3. **认领即归属**：第一个认领的人锁定该物品，之后**其他人不能再认领**（数据库侧拒绝）。
4. 同一人重复提交视为更新（改姓名/手机号），不产生第二条记录。
5. 拾主不能认领自己发布的物品；拾主也不能在物品被认领后撤单。
6. 已认领的物品仍然留在失物墙上，带「已认领」标签。

### 3.4 我的

- **我的发布**：自己的全部物品（含已认领、已撤单）；状态徽标为「寻找失主中 / 已认领 / 已撤单」。
  只有在**还没被认领**（published）时可以「撤单」；可查看该物品的**认领人名单**。
- **我的认领**：自己提交过的认领记录（姓名、手机号、时间），可随时回看已揭晓的联系方式/位置。

### 3.5 状态机

```
published ──(第一个认领人提交)──> claimed    （仍在墙上，带标签；拾主不能撤单）
    └──────(拾主撤单)─────────> withdrawn  （从墙上消失，仅拾主可见）
```

### 3.6 界面与交互原则（第 2/3 轮 UI 改造）

本轮目标是「操作尽可能少、每一屏尽可能空」。完整规范见 `docs/UI-DESIGN.md`，硬约束四条：

1. **没有底部导航栏**；全站唯一的「我的」入口在**首页右上角**，其余页面靠「返回」退栈。
2. **一步一屏**：需要多步的操作必须拆屏，每屏只问一件事、只有一个主按钮；禁止长表单。
3. **文案尽量短**：标题 ≤8 字，说明最多一句 ≤20 字，删除免责声明式段落。
4. **动效用 `motion`，只做正反馈**：发布成功整屏对勾、领取后展开揭晓、标记已找回后卡片淡出、步骤左右滑动、瀑布流依次入场；统一走 `components/motion/primitives`，并由 `MotionProvider` 在系统「减少动态效果」时自动退化。

## 4. 安全与隐私模型（本轮的重点，且与上一版**方向相反**）

### 4.1 关键决策变更

上一版曾要求「**从后端禁止获取全部物品列表**，防止被人用来偷窃」。本轮用户改判为**公开的失物墙**。
因此防护重心从「行级不可见」转为**列级保密**：

| 层          | 做法                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 行级（RLS） | 登录用户可读 **status <> 'withdrawn'** 的全部物品（含已认领），以及自己名下的全部物品                                                                          |
| **列级**    | `contact / location_lat / location_lng / location_label` 对 `anon` 与 `authenticated` **REVOKE SELECT**，客户端任何查询碰这些列都直接 42501（包括星号 select） |
| 写入        | 三张业务表对客户端**只有 SELECT**，没有任何写权限；所有写入必须经 SECURITY DEFINER RPC                                                                         |
| 揭晓        | `reveal_found_item_contact` 仅**拾主本人**或**已提交认领记录的人**可调用                                                                                       |
| 认领人信息  | `pickups` 的可见性为**拾主 + 认领人本人**（RLS）                                                                                                               |
| 图片        | 私有桶，无任何客户端读写策略；上传走 `/api/upload`（service_role），读取由服务端签发 1 小时签名 URL                                                            |

### 4.2 数据表

```
found_items        id, owner_id, title, description, custody, contact, location_lat/lng/label,
                   status(published|claimed|withdrawn), created_at, updated_at,
                   claimed_at, withdrawn_at
found_item_images  id, found_item_id, storage_path, position
pickups            id, found_item_id, picker_id, picker_name, picker_phone, created_at
                   unique(found_item_id, picker_id)
profiles           id, username, created_at, updated_at
app_config         max_photos(5), page_size(20)   —— RLS 全禁，只能经 RPC 读
```

已删除：tags / found_item_tags / lost_reports / lost_report_tags / matches / claims / claim_attempts。

### 4.3 RPC

| RPC                                         | 调用方         | 作用                                                                                                            |
| ------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------- |
| `publish_found_item(...)`                   | authenticated  | 一次事务建物品与照片；校验每个 path 前缀必须是调用者 uid                                                        |
| `withdraw_found_item(p_item_id)`            | 物品 owner     | 撤单；**仅 status=published 时允许**（已认领 → P0001）                                                          |
| `create_pickup(p_item_id, p_name, p_phone)` | authenticated  | 实名认领；**成功即把物品置为 claimed**；已被别人认领/已撤单 → P0001；拾主认领自己的 → 42501；本人重复提交为更新 |
| `reveal_found_item_contact(p_item_id)`      | 拾主或已认领者 | 返回联系方式或位置                                                                                              |
| `get_app_config()`                          | authenticated  | 返回 max_photos / page_size                                                                                     |

> **实现约定**：RETURNS TABLE 的 OUT 参数一律加 `out_` 前缀。本项目已因 OUT 参数与列名撞名踩过两次
> 42702（`record_claim_attempt` 的 `status`、`upsert_tags` 的 `aspect`），务必保持该约定。

## 5. AI 能力（只剩视觉）

**整套 AI 能力只有一件事：拍照 → 物品名称 + 物品描述。** 出题、判分、标签、相似度匹配全部移除。
实现方式是 **Vercel AI SDK**（`ai` + `@ai-sdk/openai-compatible` + `generateObject`，schema 由 zod 定义）。

- 默认 `AI_PROVIDER=mock`：完全确定性、零网络，供开发与自动化测试使用。
- 当前真实配置：**StepFun `step-5-preview`**（`AI_BASE_URL=https://api.stepfun.com/v1`），已用 `pnpm test:live` 实测可用。

### 5.1 接入 step-5-preview 时踩到的坑（已固化在 `lib/ai/ai-sdk.ts`）

| 现象                                                                                                                                                         | 处理                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 它是推理模型，reasoning 占用 completion token；max_tokens 给小了会 finish_reason=length 且 content 为空                                                      | `maxOutputTokens=16000`                                           |
| `reasoning_effort=high` 在结构化抽取上会崩坏（title 变成乱码、字段混入 base64）                                                                              | 固定 `reasoningEffort=low`                                        |
| `response_format: json_object` 不可靠（实测返回空对象）                                                                                                      | 只用 `json_schema`（即 `generateObject`）                         |
| `createOpenAICompatible` 的 `supportsStructuredOutputs` **默认为 false**，不开它 provider 根本不发 json_schema，`generateObject` 会退化成「靠提示词求 JSON」 | 显式 `supportsStructuredOutputs: true` + `strictJsonSchema: true` |
| 自由键的 object（additionalProperties）会被填成空字符串                                                                                                      | schema 只用扁平字段（title / description）                        |
| 拍照建议需要「通过 / 补拍」两态，boolean 字段不够稳                                                                                                          | 用字符串枚举 `verdict: ok                                         | retake`（实测返回「物品不完整，请退后拍全貌」） |
| `{ type: "image" }` content part 已被 AI SDK 弃用                                                                                                            | 改用 `{ type: "file", data, mediaType }`                          |
| 本地图片是私有桶签名 URL，主机名 `127.0.0.1`，**远端模型无法访问**                                                                                           | provider 先在服务端下载成字节再发送                               |
| providerOptions 的键必须是 camelCase                                                                                                                         | provider name 用 `stepfun`                                        |

- 离线基线（`pnpm test:unit` / `test:rls` / `test:e2e`）与 E2E 的 dev server 都**强制 `AI_PROVIDER=mock`**（见 `tests/setup.ts` 与 `playwright.config.ts`）。
- 真实模型只用于 `pnpm test:live` 与手工验证。

## 7. 验收标准

1. 登录后首页是双列瀑布流，卡片只有图片/名称/描述/时间；分页可加载更多。
2. 发布：拍照 1–5 张 → 识别出名称与描述（可编辑）→ 选代为保管并填电话 → 发布成功并出现在失物墙。
3. 发布：留在原地 + 位置描述（或定位）也能发布成功。
4. **隐私**：另一个账号在列表与详情页**看不到任何联系方式或位置**；直接查库/调 API 读取这些列必须 42501。
5. 认领：在**独立一屏**填真实姓名 + 手机号提交后，**立即揭晓**拾主的电话或位置，且物品状态变为 `claimed`。
6. 拾主在「我的发布 → 查看认领人」里能看到认领人的姓名与手机号。
7. **已认领的物品仍然出现在失物墙上，并带「已认领」标签**；其他人不能再认领（数据库侧拒绝）。
8. 拾主「撤单」后物品从失物墙消失、他人访问 404；**已被认领后不能撤单**；同一认领人重复提交不产生多条记录。
9. 移动端（Pixel 7）无横向溢出，loading/成功/失败反馈完整。
10. `pnpm verify` 全绿（typecheck + lint + unit + rls + e2e）。
11. **无底部导航栏**；首页右上角存在「我的」入口；`/me` 用标签页把「我的发布」「我的认领」分成两屏。
12. 发布流程三个屏幕，任一时刻只出现一个屏幕的表单内容（拍照屏不得出现名称/描述/联系方式输入）。
13. 关键操作有动效正反馈，且动效不影响可交互性（元素始终在 DOM 中，断言不因动画而丢失）。
14. 发布第 2 屏在 AI 生成期间是**全屏加载**：此时 `#title`/`#description` 在 DOM 里计数为 0（不得出现「骨架屏 + 输入框」两套）。
15. 拍照后 AI 给出建议：建议补拍时底部并排「继续拍照」+「下一步」；建议通过时只有一个主按钮；建议永不阻塞流程。
16. 内容量不大的屏（首页空态、`/me` 空态、认领屏、发布第 1/3 屏）内容与主按钮**整体垂直居中**。
17. 详情页图片可用手指左右滑动切换，且左右按钮/圆点仍可点、页面无横向溢出。
